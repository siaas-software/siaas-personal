# RC3 native testing — Windows, macOS and Linux

RC3 preparation does not establish native installation acceptance. Public RC3
assets use the isolated source installer contract described in `RELEASE_NOTES.md`.
Within the repository see [RC3 notes](1.1.0-rc.3.md).

## Native package restriction

Native packages keep app ID `it.siaas.desktop`, product name `SIAAS Personal`,
the Windows application identity, Linux package name `siaas-personal`, and the
default Electron `SIAAS` data profile. A different filename or installation
directory does not make these packages safe to install beside stable.

**Native installer testing is permitted only in a disposable VM with no existing
SIAAS installation or personal data, no mounted host profile, and a clean snapshot.**
Do not install them on a stable user's machine or treat another directory as
isolation. Restore the snapshot after testing. This release deliberately excludes
native packages from the public inventory; `release:verify-source` rejects any
extra native artifact. No broad application-identity migration is introduced.

## Build and artifact checks

Use the reviewed RC3 commit, the committed lockfile and Node 24.22.0 on the native
host. Run `npm ci`, `npm test`, `npm run typecheck`, `npm run desktop:build` and
`npm run desktop:prepare`. Check `.desktop/app/package.json` is `1.1.0-rc.3` and
`.desktop/resources/runtime/version.json` records Node 24.22.0 and the target.
Build using electron-builder with `--config electron-builder.cjs --publish never`.
Keep the output outside the release's `dist-source` inventory. Generate hashes
with `node scripts/checksums.mjs` and verify them before transferring into the VM.

Configured native targets:

| Host/architecture | Formats | Acceptance |
| --- | --- | --- |
| Windows x64 | NSIS EXE | Not run |
| macOS x64, arm64 | DMG and ZIP | Not run |
| Linux x64 | AppImage and DEB | Packaging and runtime are separate checks |

Windows/Linux arm64 source manifests do not establish native installer support.
Native update-manifest generation remains stable-only and is not an RC3 gate.
Do not upload generated `latest*.yml`, `update-*.json` or native installer files.

## Acceptance record for each VM

Record OS/build, architecture, source SHA, artifact name/hash, Node/Electron
versions, signature/notarization status, commands, results and logs. Mark failures
as FAIL, unavailable prerequisites as BLOCKED, and untouched cases as NOT RUN.

1. Confirm the VM snapshot is clean and contains no stable installation or real
   user data. Test with a normal user. Inspect the package and verify its digest.
2. Install through the normal OS flow. Record Windows SmartScreen/Defender and
   PowerShell policy, macOS quarantine/Gatekeeper, or Linux FUSE/sandbox/library
   requirements. No `--no-sandbox`, `chromiumSandbox: false`, execution-policy
   bypass, quarantine removal, disabled antivirus or relaxed OS protections.
3. Launch, confirm RC3 version and the official icon. Verify the local server
   binds to loopback, renderer sandbox/context isolation stay enabled, and an
   unrelated client cannot access the desktop API.
4. Exercise all six templates, palette consistency, creation/import/export,
   assistant model selection, Knowledge, Actions and structured CSV/XLSX analysis.
   Use the existing RC2 budgets fixture for arithmetic and mixed-currency checks.
   Separate mocked inference from real Ollama/model results.
5. Save test projects and conversations, restart, and verify persistence. Confirm
   shutdown stops owned processes and releases files. Record interrupted-start and
   interrupted-install behavior; PR #20's draft test improvements are not included.
6. In the disposable VM only, test reinstall/uninstall and an explicit update/
   rollback scenario. Verify expected data retention; rollback is not a database
   migration undo mechanism. Do not claim an automatic native RC update path.
7. For source installs, use the explicit RC3 root in the release notes. Verify the
   root's `profile` and `launch-rc.*`, managed runtime hash, and failed-stage
   preservation. If testing RC2-to-RC3 update/rollback, use a dedicated test root
   containing only synthetic RC2 data, never the user's existing RC2 installation.
8. Preserve evidence outside the VM, then restore its clean snapshot.

## Known limits

Unsigned artifacts have no verified publisher identity. Windows may warn or block;
macOS Developer ID/notarization and Finder acceptance are unverified. An OS block
is a valid reported limitation, not a reason to weaken protections. Linux package
construction does not prove graphical startup or installation.

The cloud environment used for preparation cannot currently launch sandboxed
Chromium: the SUID helper prerequisite fails. Native Electron requires a compatible
graphical/sandbox host. Real Ollama is unavailable there. These environmental
limitations remain under the existing RC policy, not new exemptions or PASS claims.
