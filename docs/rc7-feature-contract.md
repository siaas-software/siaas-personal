## Architectural invariants

- Keep Project, Assistants, Actions, **Skills**, Project Templates as distinct user-facing concepts. The new Skills interface is maintainer-authorized on 2026-11-23; earlier decisions prohibiting a Skills registry are superseded. Project orchestration remains optional; each assistant retains its own Hybrid Router, Ollama model, Knowledge, and runtime tools. No Agent Context Builder, dynamic supervisor, second router or prompt-driven executor.
- **Actions** represent explicit user-invoked tasks (instruction-only or registered native capabilities). **Skills** represent portable procedural guidance (how to do a task), assigned to projects and enabled for assistants, based on portable SKILL.md. Existing custom Markdown Actions must remain safe and backward-compatible. Neither Action nor Skill text adds executable code, permissions or new tools.
- Add **Tool Permission Gateway** at project level with explicit `Allow / Ask / Deny` rules, editable defaults and user-created exact capability rules. The decision must run at **every** native, MCP and media tool invocation, including delegated assistant calls. Unknown/unregistered tools DENY; cross-project access/credential theft/arbitrary shell remain forbidden regardless of user or imported template text. Model output does not confer permission.
- Preserve assistant-specific source permissions and project membership checks; allow is necessary but insufficient. `Ask` blocks until an authenticated **operation-specific** approval, with cancel/deny and event evidence; it is not an alias for Allow. Avoid persisted blanket privilege escalation and use least privilege for targets, file paths and MCP tools.
- `AGENTS.md` is an on-demand **derived preview**, displayed read-only under project settings with **Copy**. It is never stored as a separate entity or included in export/import. Never use rendered Markdown as the security source of truth.
- Project Template export/import should eventually carry **project-linked Actions** (portable definitions/references, conflict-handled) and project permission rules with safe import confirmation. Preserve v1/v2 import and pristine RC6 templates; version portable format explicitly if schema changes. Do NOT add `AGENTS.md` to the template payload or silently copy credentials, absolute paths, assistant UUIDs, model weights, histories or indexed Knowledge.

## MCP servers — phase C implementation

1. Support locally configured MCP clients to **stdio** servers (local processes, explicit executable/args/environment allowlist) and approved remote streamable HTTP endpoints where protocol support and security can be verified. No mandatory public/cloud service; no Docker requirement. Local-first behavior with Ollama optional for deterministic tools.
2. Implement lifecycle: explicitly added server configs, validate/connect/disconnect, capabilities listing, per-tool JSON schemas, server status/errors, timeouts, cancellation, restart/cleanup, secrets redaction, output limits, log safety. Host/network and redirect restrictions prevent SSRF, credentials in URLs and unapproved local network reachability; remote access requires informed user consent.
3. Bind discovered tools to current **assistant** and project, never globally shared implicitly. Tool invocation enters the existing assistant executor + project orchestration, and must check registry, Gateway decision, current assistant source limits, scope, user `Ask` approval, budgets and typed results. Never treat MCP tool descriptions/results as privileged instructions. Tool-name collisions and server config changes invalidate previous approvals.
4. Negative tests: adversarial tool descriptions, malformed schema, revoked server/config, slow/hung processes, disconnect mid-run, unauthorized project, private IP redirects, prompt injection, unknown tool, unapproved write, invalid approval token, restart, offline no-Ollama deterministic fallback, Windows/macOS/Linux launch and clean shutdown.

## Local Media Engine — phase C implementation (approved 25 November 2026)

1. Introduce a minimal internal Media Engine service, not a new user-facing entity, editor, router, scheduler or standalone server. Reuse the assistant executor, Hybrid Router, registered native Actions, Skills (procedural only), project Gateway and Unified Execution Trace. The existing two official Studio presets remain acceptance examples.
2. Use **stable-diffusion.cpp as the sole generative backend** for image/video generation and **FFmpeg for deterministic media processing** (image resize, overlay, composition, video assembly from images, transitions, transcoding and inspection via ffprobe if supplied). Prefer deterministic processing whenever it satisfies the request; generation may create missing assets, followed by deterministic composition. Explicit native processing requests must work without Ollama or generation models. No mandatory Python, Docker, ComfyUI, cloud or paid provider.
3. Settings → Media Engine (proposed label): disabled by default; optional verified components/models with explicit download/install consent, source/hash/license checks, availability/status and hardware detection. Select only compatible installed models. Detect CUDA/Metal/Vulkan/other supported builds and CPU capabilities; actual driver/build/model compatibility must be tested. No automatic CPU fallback; explicit opt-in only where practicable. No custom GPU allocator. Start with one concurrent media job per runtime/profile; coordinate with other existing resource users where feasible, without introducing a second orchestration engine.
4. Use bounded typed capabilities for generate image/video and process image/video; no arbitrary FFmpeg arguments/filter graphs, executable selection from prompts, shell interpolation, network protocols or uncontrolled file access. Validate dimensions, frames, duration, CPU threads, estimated RAM/VRAM and output quota; use enforceable limits where the OS/backend supports them and label other budgets as estimates, not guarantees. Reject unsupported models or unsafe allocations; do not promise video on every machine. Evaluate Wan 2.1 1.3B only if verified compatible.
5. Apply project Allow/Ask/Deny and assistant scope on each invocation, operation-specific approvals, explicit install consent, authorized output destinations, no unintended overwrite, cancellation/timeouts, bounded child-process lifecycle, sanitized temporary paths, atomic publish after format/dimension/duration/integrity inspection, cleanup and metadata-only trace. No Skill/template grants new permissions. No external transfer by default.
6. Acceptance: real deterministic image and photo-to-video composition without Ollama/model, real image generation on supported configurations, real video generation on at least a verified supported configuration before advertising it; unavailable hardware/model must fail clearly. Test Windows i7/Iris Xe Vulkan candidate and CPU where feasible, macOS/Linux supported builds, resource pressure, model license/absence, cancellation, output validation, path escape, malicious FFmpeg inputs, revocation, Ask denial, wrong project, no silent fallback and no residual workers. Report exact versions, hardware, timing and PASS/FAIL/BLOCKED/NOT RUN. No mock-only readiness claim.
