# SIAAS Personal — development instructions

## Scope and product invariants

- Read the current task, this file, [CONTRIBUTING.md](CONTRIBUTING.md), and the relevant source before editing. Task-specific limits override broader standing permissions. Keep changes focused; preserve unrelated work.
- SIAAS Personal is a free, MIT-licensed, local-first and privacy-first desktop application. Preserve Windows, macOS and Linux support, Electron, and the existing Next.js/React architecture. Keep [LICENSE](LICENSE) and third-party/model license obligations intact.
- Inference uses local Ollama; application data stays local. Do not introduce cloud inference, accounts/authentication, Supabase, PostgreSQL, paid services, mandatory Docker, or unnecessary dependencies.
- Do not upload local documents, conversations or derived data to external services. Standard configured-website consultation is distinct from optional web discovery; preserve consent, public-URL validation and source-routing privacy boundaries.

## GitFlow, isolation and authority

- Inspect fresh `main` and `develop`, their differences, the actual default branch, applicable protections and relevant open PRs. Use read-only GitHub checks; report inaccessible settings as NOT VERIFIED rather than inferring enforcement from this file. Never probe protection by pushing to a protected branch.
- `main` is the stable/default branch; `develop` is normal integration. Fetch `origin`, then create a unique `feature/<description>` from the latest `origin/develop`. Existing cloud tasks are isolated: use the checkout and feature branch; create a worktree only when requested. Preserve existing changes before switching, and never modify another PR's branch.
- Commit only intended files, push the feature branch normally, and open its PR explicitly against `develop`. Do not merge, force-push, alter repository settings/protections, or delete refs without explicit authorization. A task requesting only instructions/documentation does not authorize release operations.
- Follow current protection/review requirements without bypass. The contributor policy requires PRs and resolved review conversations for `main`/`develop`, blocks force pushes/deletions, and protects `v*` tags against updates/deletions. It currently specifies zero approving reviews for the sole maintainer; do not confuse this with permission to bypass PR review requirements.
- Release exceptions: `release/<version>` starts from integrated `develop`; stable promotion uses a PR into `main`, then synchronization back to `develop`. `hotfix/<description>` starts from `main`, with PRs into `main` and `develop` (and an active release branch when applicable). Preserve ancestry with merge commits for release/hotfix/long-lived synchronization; do not use routine cherry-picks between long-lived branches. These are routing rules, not merge authorization.
- Keep GitHub Actions disabled; existing workflow files have `.disabled` suffixes. Do not add hosted CI, paid testing infrastructure or deployment changes to satisfy local checks. Older deployment instructions suggesting tag-triggered Actions are not evidence of an active workflow.

## Data, inference and security constraints

- Preserve Electron `contextIsolation`, disabled `nodeIntegration`, renderer sandboxing, loopback binding and origin/key protections. Do not expose the local database through the web-only entrypoint or weaken safeguards to make cloud tests pass.
- Preserve `OLLAMA_BASE_URL` validation: HTTP loopback only, with no credentials or redirects to cloud inference. Models are selected per assistant; embeddings have a separate identity/profile. A mocked Ollama response does not verify model inference or tool support.
- Preserve project/assistant ownership checks across routes, retrieval, structured datasets, relationships, conversations and reports. Actions/templates have their own workspace scope; do not incorrectly make all data assistant-scoped.
- SQLite is authoritative; Knowledge manifests/indexes are derived. Preserve migrations, foreign keys, rollback compatibility, source freshness checks, deletion semantics and user data. Imported managed copies and externally linked originals have different lifecycles; never delete linked originals as cleanup.
- Structured parsing runs in a bounded worker. Keep archive/resource limits, formula/error/cached-value distinctions and explicit review of ambiguous mappings. Never execute spreadsheet formulas, macros, arbitrary expressions, SQL or model-generated code.
- Analytical plans are schema-validated and run read-only against authorized datasets in the TypeScript engine. Preserve operation/time/output budgets, precision, partitions, relationship/cardinality checks, freshness, provenance and explicit truncation. SQLite stores datasets/results; it is not an arbitrary analytical SQL executor. Model explanations and RAG excerpts must not substitute for computed totals. See [the structured guide](docs/structured-data-analysis.md).
- Advanced Reasoning (Beta) and Advanced Web Research (Beta) are independently opt-in and off by default. Docker is optional and required only by these supported Beta stacks; standard chat, Knowledge, structured analysis and configured websites work without it. Preserve prerequisite checks and per-assistant web-discovery consent. See [the research guide](docs/research-en.md).
- Preserve `siaas-project-v1`: portable templates carry configuration/public source URLs, with model selection reset to `null`; never include documents, local paths, chats, embeddings or indexing data. Do not hand-edit generated catalog snapshots.

## Development commands and validation

Run commands from the repository root. Use the Node engine in [package.json](package.json) (currently `>=22.16.0`) and [runtime.json](runtime.json) for managed distribution; do not hard-code remembered dependency versions. Install with `npm ci`, preserving the lockfile and integrity/TLS checks. `npm run desktop:install` additionally installs Electron and builds the desktop runtime. Prefer writable external caches when the cloud home is restricted.

| Check/workflow                  | Commands and prerequisites                                                                                                                                                                                                                                                                                                   |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Automated tests                 | `npm test` runs the TypeScript/CJS test globs; `.mjs` integration suites are separate. Use `npm run test:structured`, `test:actions`, `test:experimental`, `test:research` as relevant.                                                                                                                                      |
| Static/build checks             | `npm run typecheck`; `npm run templates:check`; `npm run build`; `npm run desktop:build`. Desktop build creates `.next/standalone` and bundles the structured parser and legal notices. Web/desktop builds share `.next`; rebuild desktop before its integration suites.                                                     |
| SQLite/API integration          | After desktop build: `npm run test:chat`, `npm run test:knowledge`, `npm run test:actions:api`, `npm run test:structured:api`, and `node tests/template-api.mjs`. These exercise real local HTTP/SQLite with temporary data and simulated Ollama. `node tests/structured-bundle.test.mjs` validates parser bundling/notices. |
| UI/visual                       | After desktop build: `npm run test:ui`, `npm run test:structured:ui`, `npm run test:actions:ui`, and relevant targeted scripts in [tests/](tests/). Requires a compatible Playwright browser. Inspect each script's executable-path options; do not assume one browser variable applies to all.                              |

| Distribution, when in scope     | `npm run test:installer`, `npm run test:distribution`, `npm run icons:check`; `npm run desktop:prepare`, `npm run test:package`, `npm run desktop:package` (configured with `--publish never`). - For application changes run the README's core automated/type/build checks and relevant regressions. Chat routing, structured analysis, Knowledge/RAG, persistence, installers and updates require regression coverage in their existing suites; include restart/isolation/security cases when affected. Do not weaken tests or alter assertions merely to obtain PASS.
- For instructions-only changes, validate Markdown structure, all local links, `git diff --check` and the full diff. Do not run packaging, installers, AI model downloads or unrelated application suites solely for documentation changes.
- Record exact commands and current outcomes: PASS, FAIL, BLOCKED (specific external prerequisite), or NOT RUN/NOT VERIFIED. Confirm tests actually executed; never copy historical counts or treat a zero-test run as coverage. Investigate actual failures separately from environment limitations.
- Cloud sandbox restrictions, unavailable browsers, Docker, Ollama/models or graphical/native hosts can block checks. Record the observed reason without bypassing Electron/OS protections, disabling verification or claiming success. Cross-builds and headless API/browser tests do not establish native Windows EXE/icon/installation, macOS, Linux Electron or real-model acceptance. Recheck prerequisites only after a material change.

## Releases and installation safety

- Read [the permanent RC publication policy](docs/rc-publication-policy.md) and [CONTRIBUTING.md](CONTRIBUTING.md) before RC work. Its standing authorization applies only to applicable RC preparation/publication scope and remains subject to narrower task instructions. Do not tag, package for distribution, publish or deploy during an AGENTS/documentation-only task unless specifically requested.
- An applicable, authorized RC workflow may proceed automatically only after all mandatory executable gates pass: automated/type/desktop checks, applicable packaging/distribution, installer/archive/manifest/checksum integrity, simulated Chat/Knowledge/Actions/structured regressions, consistent versions/assets, no unresolved critical defect, and satisfied GitFlow protections. Actual test failures and corrupt artifacts remain blockers.
- The policy's enumerated environment-blocked real Ollama, Chromium, Linux Electron and native Windows/macOS checks are honestly recorded manual acceptance activities; they do not automatically block an otherwise authorized RC while the stated limitations persist. Do not classify an executable failing test as environmental or add unavailable platform gates without authorization.
- Candidates use reviewed release branches from integrated `develop`, RC versions in both package manifests, GitHub prerelease enabled and Latest disabled. Keep stable `main` and the stable installer/update channel separate; candidate installers/profiles must stay isolated. Never move existing tags or replace immutable released assets.
- Stable publication always requires explicit authorization. A feature PR, commit, successful build, old release report or RC standing permission does not authorize stable promotion or website deployment.
- Before release claims verify the exact commit/tag, GitHub draft/prerelease/Latest status, asset identities, manifests and checksums; verify anonymous downloads for publication. Report inaccessible release metadata as NOT VERIFIED, not as a current release fact.
- For end-user installation/system modification, explain OS/architecture, paths, downloads, storage/hardware/local-model limitations and obtain informed authorization unless already provided. Use official verified artifacts, preserve data and OS protections, and verify actual launch. A recommendation request is not installation consent.

## Cross-repository consistency and delivery

- `siaas-templates` owns template definitions/contracts. Check [templates-source.json](templates-source.json); update via `npm run templates:sync -- --ref <full-commit-sha>` (or the supported local `--catalog` option), then `npm run templates:check`, only when template changes are in scope.
- `siaas-documentation` is private engineering documentation: decisions, evidence and test reports. Never copy private internal documentation into public assets, release notes or PRs.
- `siaas-public-site` owns public user-facing documentation/site. Follow [the language/synchronization policy](docs/documentation-language.md). Report discrepancies or inaccessible sources; do not silently edit another repository. Keep root/unqualified engineering instructions in English and localized guides consistent with actual interface labels.
- Before delivery inspect `git status`, staged paths and the full final diff; run `git diff --check`. Report changes, evidence and remaining risks. Open the PR without merging. If PR creation returns Forbidden, provide the pushed branch, full commit SHA and `https://github.com/siaas-software/siaas-personal/compare/develop...<branch>` URL; do not invent a PR number or claim one exists.
